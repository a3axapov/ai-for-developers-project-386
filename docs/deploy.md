# Развёртывание на Render

Приложение разворачивается как один Docker-контейнер: Spring Boot отдаёт API и
статический React-бандл на одном origin. Render собирает образ из `Dockerfile`
в корне репозитория и выставляет переменную окружения `PORT`; приложение читает
её через `server.port: ${PORT:8080}`.

Описание инфраструктуры хранится в [`render.yaml`](../render.yaml): Blueprint,
ветка `main`, Docker runtime, health check `/api/health`, автодеплой по пушу.

Публичный origin для абсолютных ссылок в `.ics` берётся из
`CALENDAR_PUBLIC_ORIGIN`. В Render эта переменная не нужна: платформа сама
выставляет `RENDER_EXTERNAL_URL` (`https://<service>.onrender.com`), и приложение
использует его как значение по умолчанию. При подключении собственного домена
задайте `CALENDAR_PUBLIC_ORIGIN=https://<домен>` в переменных сервиса.

## Первый деплой

1. После независимого ревью выполнить `mise run check` на окончательном коде,
   отправить `main` в GitHub и дождаться зелёного CI именно опубликованного SHA.
2. Через Render MCP проверить workspace `hexlet` и существующие сервисы.
   Проектная конфигурация MCP и безопасная передача `RENDER_API_KEY` описаны в
   [README](../README.md#mcp); значение ключа не записывать в Git или отчёты.
3. Вызвать `create_blueprint` с URL репозитория, `branch: main`,
   `path: render.yaml`, `existingResources: create_new` и подтверждённым
   `workspaceId`. Проверить возвращённый план: только один бесплатный Docker
   web service в Frankfurt, без базы, диска и платных ресурсов. Создание плана
   ещё не разворачивает приложение.
4. После согласования фактического плана вызвать `approve_blueprint`.
   Не утверждать неуспешный план и не создавать второй сервис при ошибке
   без проверки состояния первого запроса.
5. По полученным service/deploy ID дождаться статуса **Live** и сверить commit
   деплоя с проверенным SHA. Render назначит HTTPS-адрес вида
   `https://<service>.onrender.com` и передаст контейнеру `PORT`.
6. Пройти проверки ниже по публичному адресу. Записать фактические ссылки
   приложения, владельца и гостя в README (раздел «Демо») и #34; в тикете также
   сохранить deployed SHA, deploy ID, команды, результаты и ссылку CI.

Публичный адрес фиксируется только после первого успешного деплоя.
Для этой поставки выбран именно Render MCP, а не ручное создание сервиса
через Dashboard. Dashboard можно использовать для просмотра состояния.

## Адреса

| Путь                                  | Назначение                                           |
| ------------------------------------- | ---------------------------------------------------- |
| `/`                                   | Главная страница                                     |
| `/admin`                              | Раздел владельца (без авторизации)                   |
| `/booking/<username>`                 | Публичная страница записи, например `/booking/owner` |
| `/booking/<username>/<meetingTypeId>` | Прямая ссылка на тип встречи                         |
| `/bookings/<accessToken>`             | Результат записи гостя                               |
| `/api/health`                         | Техническая проверка, `{"status":"UP"}`              |

## Подготовка демо

После старта экземпляра данные пустые (кроме исходного профиля из
`src/main/resources/application.yaml`). Чтобы получить публичную ссылку:

1. Открыть `/admin`, включить публичную запись.
2. Создать тип встречи и скопировать его ссылку `/booking/owner/<id>`.
3. Эта ссылка и есть публичная запись для проверяющего.

## Проверки после деплоя

- `GET /api/health` → `200` и `{"status":"UP"}`.
- Открытие страниц и обновление (F5) страниц `/`, `/admin`, `/booking/owner/...` и
  `/bookings/...`.
- Неизвестные пути отдают настоящие 404: `/api/does-not-exist`,
  `/assets/does-not-exist.js`.
- Гость проходит сценарий: тип → дата → время → имя, email, комментарий →
  результат; владелец видит запись в общем списке.
- Повторная одновременная запись на тот же слот через API получает
  `409 TIME_CONFLICT`, второго бронирования нет.
- Проверить пересечение разных типов: 60 минут с 10:00 и 30 минут с 10:30.
  Попытки подготовить до первой записи, затем отправить последовательно:
  первая создаётся, вторая получает `409 TIME_CONFLICT`. Подготовленная попытка
  не резервирует время. Гость видит понятный отказ и обновлённый календарь;
  владелец видит только созданную встречу.
- После рестарта или редеплоя данные сброшены, старые ссылки на результаты и
  попытки недоступны.

## Данные и сброс

Состояние хранится **в памяти одного экземпляра**. Рестарт, редеплой и
пересоздание контейнера сбрасывают профиль, доступность, типы встреч,
бронирования, отпуска и блокировки. На бесплатном плане Render дополнительно
усыпляет сервис после периода без запросов: при пробуждении состояние тоже
сбрасывается, а первый запрос может отвечать дольше обычного.

## Ограничения

- Один экземпляр; горизонтальное масштабирование и общие хранилища не
  поддерживаются.
- Нет базы данных, авторизации и полного CD: раздел `/admin` открыт всем, HTTPS
  не защищает его.
- Нет постоянного диска; файлы и состояние не переживают пересоздание.

## Обновление и остановка

- Пуш в `main` запускает автодеплой; ручной редеплой — кнопкой **Manual Deploy**
  в Render Dashboard или через MCP. Автодеплой требует подключённого Git-провайдера;
  для сервиса из публичного URL без подключения провайдера нужен ручной деплой.
- Остановка — **Suspend**; удаление сервиса освобождает адрес `onrender.com`.
