# Сервис бронирования встреч

Сервис, где владелец календаря публикует доступное время для встреч, а гость выбирает свободный слот и записывается на звонок — без регистрации.

## Возможности

- Владелец заполняет профиль, задаёт рабочие часы и исключения, создаёт типы встреч и управляет бронированиями.
- Владелец ведёт внутренний календарь сервиса: занятое время проверяется на конфликты, новые встречи добавляются в календарь автоматически.
- Гость переходит по публичной ссылке, выбирает тип встречи и свободный слот в календаре на ближайшие 14 дней.
- Система не позволяет занять одно и то же время дважды, даже разными типами встреч.

## Ограничения

- Нет авторизации и личных кабинетов.
- Нет интеграций с внешними календарями: календарь ведётся внутри сервиса, а гость может скачать файл `.ics`, чтобы добавить встречу в свой календарь вручную.
- Владелец календаря в приложении один и задан заранее.
- Горизонт записи для гостя — ближайшие 14 дней.

## Роли

### Владелец

Единственный пользователь сервиса, задан заранее. Работает в разделе «Админка», доступном по отдельной выделенной ссылке.

### Гость

Человек, который записывается на встречу. Аккаунт не нужен: гость заходит по ссылке, опубликованной владельцем.

## Сценарий работы владельца

1. **Настройка профиля и календаря.** Заполнить профиль (имя и username — от него зависит публичная ссылка для записи), создать внутренний календарь. Сервис проверяет календарь на конфликты и добавляет в него новые встречи.
2. **Настройка доступности.** Задать рабочие часы и часовой пояс, при необходимости создать несколько расписаний и исключения для отдельных дат, отметить отпуск через «Out of office».
3. **Создание типов встреч.** Например, «Консультация 30 минут»: название, описание, длительность. У каждого типа встречи своя ссылка для записи.
4. **Публикация ссылки.** Отправить ссылку на страницу бронирования клиентам, разместить её на сайте или в соцсетях.
5. **Работа с бронированиями.** Проверять предстоящие встречи, подтверждать или отклонять запросы, при необходимости переносить и отменять встречи.

## Сценарий работы гостя

1. **Получение ссылки.** Гость получает ссылку от владельца: в письме, на сайте, в соцсетях или в мессенджере.
2. **Выбор типа встречи.** На странице бронирования гость видит список типов встреч с названием, описанием и длительностью и выбирает подходящий.
3. **Выбор времени.** Открывается календарь на ближайшие 14 дней. Слоты показываются в часовом поясе гостя. Занятые часы и исключения владельца уже учтены — видны только свободные слоты.
4. **Заполнение формы.** Гость вводит имя, email и комментарий.
5. **Подтверждение.** Гость подтверждает запись. Если у владельца включено ручное подтверждение, запись получает статус «ожидает подтверждения» до решения владельца.
6. **Результат.** Гость видит страницу с деталями встречи и может скачать файл `.ics`, чтобы добавить встречу в свой календарь.

## Правила бронирования

- Длительность слота равна длительности выбранного типа встречи.
- Одно и то же время нельзя занять дважды, даже разными типами встреч.
- Гость видит календарь только на ближайшие 14 дней.
- Свободные слоты рассчитываются с учётом расписаний доступности, часового пояса владельца, событий во внутреннем календаре и исключений «Out of office».

## Работа с API

Обязательная часть работы с API состоит из двух артефактов:

1. **TypeSpec-контракт** — исходное описание API сервиса.
2. **OpenAPI-спецификация** — генерируется из TypeSpec-контракта.

API-клиент генерируется по OpenAPI-спецификации и вручную не пишется.

## Разработка

### Текущий интерфейс

- `/` — главная для гостя: описание сервиса и будущих возможностей.
- `/booking` — вход на текущую публичную страницу: адрес запрашивается у сервера.
- `/booking/{username}` — имя владельца и состояние записи; неизвестный адрес
  показывает «Страница не найдена» без перенаправления.
- `/admin` — исходный профиль владельца из серверной конфигурации, доступный
  по ссылке «Владельцу».

Ссылки не требуют авторизации. Раздел владельца показывает имя, username,
часовой пояс, переключатель публичной записи и копирование общей ссылки.
Запись включается отдельным действием, даже без типов встреч. Выключенная
страница показывает «Запись временно недоступна», включённая без типов —
«Сейчас нет доступных типов встреч». Создание типов и форма записи пока не реализованы.
Редактор профиля и управление календарём появятся в следующих срезах.
Словарь предметной области находится в [GLOSSARY.md](GLOSSARY.md).

Если ответ изменения потерян, переключатель блокируется: неизвестный исход не
считается успехом или отказом. Кнопка «Выяснить результат» запрашивает сохранённый
исход той же операции, не отправляя изменение заново. Если результат недоступен
(возможен сброс данных), сначала явно загрузите актуальный профиль; новая команда
не создаётся автоматически. В другой вкладке профиль мог измениться: конфликт
показывает актуальные данные и требует нового осознанного действия.

### Исходная конфигурация и сохранность

Исходные значения находятся в `src/main/resources/application.yaml`, в секции
`calendar.initial`: имя «Владелец календаря», username `owner`, пояс `Europe/Moscow`,
публичная запись выключена, рабочие дни Пн–Пт с 09:00 до 18:00. Дни задаются
списком `working-days`, границы — `work-start` и `work-end` в формате `HH:mm`;
`24:00` допустимо только как окончание. Эти часы предназначены для новых типов
встреч, их редактор пока не реализован. Некорректные настройки останавливают
запуск с сообщением о проблемном поле.

Значения можно изменить до запуска, например подключить внешний YAML:

```sh
java -jar build/libs/calendar.jar --spring.config.additional-location=file:./owner.yaml
```

```yaml
calendar:
  initial:
    name: Анна Петрова
    username: anna-1
    time-zone: Pacific/Auckland
```

**Данные хранятся в памяти одного экземпляра сервера.** Перезапуск сервиса или
пересоздание контейнера сбрасывает состояние: изменённые профиль и доступность,
типы встреч, бронирования, отпуска, блокировки, сведения о попытках и операциях
не имеют гарантии сохранности. Сейчас реализованы профиль и выключатель записи;
это ограничение распространяется и на последующие возможности. После сброса
исходное состояние восстанавливается из конфигурации; прежние ссылки и результаты
попыток могут стать недоступны. Постоянной БД и поддержки нескольких экземпляров нет.

Стек: Spring Boot / Java 25, React / TypeScript / Vite, Gradle, JUnit,
Checkstyle, ESLint и Prettier. Версии и причины выбора описаны
в [матрице зависимостей](docs/toolchain.md).

### Подготовка

Установите [mise](https://mise.jdx.dev/getting-started.html) версии **2026.11.6**
и добавьте его в `PATH`. Для автоматического окружения в интерактивном shell
используйте `mise activate`; команды `mise run` работают и без активации.

```sh
mise trust
mise install
mise run test:browser:install
mise run check
```

`mise install` устанавливает закреплённые инструменты, затем через postinstall
запускает `npm ci` и устанавливает Git-хуки hk. В CI Git-хуки не устанавливаются.
Повторная установка зависимостей: `mise run install`.

Для локальной разработки Docker и база данных пока не нужны. Docker Engine
с BuildKit нужен для сборки и проверки поставляемого образа.

### Запуск

```sh
mise run dev
mise daemons status
mise daemons logs backend frontend
mise run stop
```

- Интерфейс: <http://127.0.0.1:5173>.
- API: <http://127.0.0.1:8080/api/health>.
- Vite проксирует `/api` на Spring Boot; CORS в разработке не требуется.
- Серверы работают в фоне под управлением pitchfork, а не через `&`.

Локальные настройки можно переопределить в игнорируемом `mise.local.toml`.
При смене портов согласованно измените `SERVER_PORT`, `VITE_PORT`,
`VITE_API_TARGET` и readiness-порты в определениях daemons.

Например, если порт 8080 занят, создайте `mise.local.toml`:

```toml
[env]
SERVER_PORT = "18080"
VITE_API_TARGET = "http://127.0.0.1:18080"

[daemons.backend]
run = "exec ./gradlew --no-daemon bootRun"
ready_port = 18080
ready_cmd = "node scripts/wait-http.mjs http://127.0.0.1:18080/api/health"
```

Переопределение daemon заменяет его описание целиком. После изменения настроек
перезапустите daemons через `mise daemons restart`.

### Контракт и клиент

```text
api/main.tsp
  → api/openapi/openapi.yaml
      ├─ api/server/                 # серверные интерфейсы Spring MVC и модели
      └─ frontend/src/api/generated/ # клиентский SDK
```

```sh
mise run api:generate
mise run api:check
```

Контракт и все результаты генерации хранятся в Git. OpenAPI, серверные интерфейсы
и модели, TypeScript-клиент генерируются, вручную не редактируются. Сервер использует
OpenAPI Generator 7.27.0 (`spring`, интерфейсы для Spring Boot 4/Jackson 3),
клиент — Hey API. Собственные контроллеры реализуют генерируемые интерфейсы.
`api:check` повторяет всю генерацию во временном каталоге и сравнивает содержимое
и полные списки файлов, включая новые и удалённые, не изменяя рабочие файлы.
`api:generate` заменяет результаты только после успешной генерации всех наборов,
удаляя устаревшие файлы. Для генерации нужны и Node.js, и Java из mise.
Публичная главная не обращается к API; `/api/health` остаётся технической проверкой.
`GET /api/owner/profile` возвращает профиль и его исходную версию; `/admin`
запрашивает его через сгенерированный SDK.

`PUT /api/owner/public-booking` принимает `enabled` и `expectedVersion`, требует
непустой `Idempotency-Key` и возвращает профиль с новой версией. Повтор того же
запроса под тем же ключом возвращает сохранённый успех или определённый отказ;
изменённые данные под прежним ключом дают `409 IDEMPOTENCY_KEY_REUSED`. Исправленный
запрос требует нового ключа. Некорректный формат даёт `400 MALFORMED_REQUEST`,
недопустимые данные — `422 VALIDATION_FAILED` с ошибками полей, устаревшая версия —
`409 RESOURCE_CHANGED` с `currentProfile`. Ошибки не меняют профиль.
`GET /api/owner/operations/{key}` возвращает сохранённые `statusCode` и `profile`
либо `error`; недоступный исход — `410 OPERATION_UNAVAILABLE`. Сведения об операциях
хранятся только в памяти до сброса. Для разобранных команд сравниваются значения
полей, для неразбираемого тела — исходный текст.

`GET /api/public/booking-entry` возвращает текущий `bookingUrl`,
`GET /api/public/{username}` — `ownerName`, `ownerTimeZone` и `state`:
`BOOKING_DISABLED` без списка либо `OPEN` с пустым `items`. Неизвестный username
даёт `404 PAGE_NOT_FOUND`. Все эти ответы используют `Cache-Control: no-store`.

### Проверки и сборка

```sh
mise run check       # API-артефакты, линтеры, типы, HTTP/JUnit, сборка приложения, Playwright
mise run format      # исправить форматирование JS/TS/JSON/YAML/Markdown и TypeSpec
mise run test        # JUnit с реальным HTTP-запросом к серверу на случайном порту
mise run build       # build/libs/calendar.jar, включая фронтенд
mise run audit       # известные npm advisories, включая инструменты разработки
mise run test:browser:install # однократно: Chromium и системные зависимости
mise run test:browser # сборка приложения и Playwright с настоящим сервером
```

Java-проверки запускаются через `./gradlew`; Linux/macOS-скрипт уже включён
в проект и должен храниться с исполняемым битом. Для Windows сохранён `gradlew.bat`.
Окончания строк задаются в `.gitattributes`. Задачи mise ориентированы на
Linux/macOS; в Windows используйте WSL.

hk запускает `mise run lint` перед коммитом и полный `mise run check` перед push.
GitHub Actions устанавливает Chromium, использует ту же команду `mise run check`,
затем собирает и проверяет Docker-образ. Playwright входит в общую команду:
проверяет профиль владельца, переходы, прямое открытие страниц, клавиатуру
и отсутствие горизонтальной прокрутки на desktop и mobile.
Браузерные тесты запускают собственные Spring Boot JAR со встроенным React
на loopback-портах 4173 и 4174 и останавливают их после прогона. Проверки чтения
используют 4173; каждый изменяющий сценарий получает новый независимый сервер на
4174 с тестовым YAML, подтверждая также, что профиль и ссылка не зашиты в интерфейсе.
Сценарии выполняются одним worker, не используют подмены ответов API; потеря связи
проверяется обрывом доставки настоящего ответа. Оба порта должны быть свободны.
Workflow Hexlet остаётся отдельным и неизменным.

### Docker

```sh
mise run image:build
mise run image:test
docker run --rm -p 127.0.0.1:8080:8080 calendar:local
```

Либо `docker compose up --build`; остановка — `docker compose down`.

Один multi-stage образ содержит Spring Boot JAR со статическим фронтендом.
Образ собирается из сохранённых серверных и клиентских результатов генерации,
воспроизводимость которых отдельно проверяет `mise run check`.
Node.js и Gradle нужны только в build-стадиях. Runtime работает от пользователя
`10001:10001`; API и интерфейс доступны на одном порту 8080.

`image:test` запускает временный контейнер на свободном локальном порту,
проверяет API, HTML, JS-ресурс, fallback клиентского маршрута и корректные 404,
затем останавливает и удаляет контейнер. Публикация образа в registry пока
не настроена: для неё нужно выбрать registry и права доступа.
